<p>把老号和新号放在一起跑，出问题时最难判断的是「到底谁连累了谁」。分组看起来是管理动作，本质上是个时间问题：账号在不同年龄段的风险特征完全不同，新号在观察期、老号在稳定期，两者需要的出口干净度和操作节奏不在一档。这篇按账号从第 0 天到第 90 天之后的时间线走一遍，说明每个阶段该分到哪一组、出口怎么排、周与月各自维护什么，让风险停在组内而不是顺着出口串到全盘。</p>

<h2>一、分组按账号年龄分，不按数量分</h2>
<p>常见的分组方式是「十个一组」「按项目一组」，这两种分法都没考虑账号本身的成熟度差别。</p>
<h3>为什么年龄是最重要的维度</h3>
<p>新号处于平台的重点观察期，任何一次环境跳变都可能被放大；老号已经有稳定的行为基线，容忍度高得多。把两者放同一条出口，等于让新号借了老号的信用，同时也把老号暴露在新号的不稳定行为里。结果是好的没变好，坏的把好的拖下水。</p>
<h3>三组起步，只定三条硬规则</h3>
<p>观察组（0 到 7 天）、成长期（8 到 30 天）、稳定组（31 天以上，含 90 天以上的老号）。规则越少越好执行：不同组不共用出口段；跨组迁移只能往前走不回退；每次迁移在表里留一行，写清时间、原组、新组、原因。组数不必多，关键是边界清晰、可追溯。</p>

<h2>二、第 0 到 7 天：观察期，出口要最干净</h2>
<p>这七天决定账号能不能活下来。此时账号没有任何历史，平台只能靠环境判断。</p>
<h3>一条出口只放一个号</h3>
<p>观察期不做任何共用。地址要选原生家宽段、同 /24 内你手上没有其他账号、近 30 天分配记录干净。这三点在采购时就要问清，别等出了问题再换——换地址本身就是一次跳变，在观察期做这件事代价最大。</p>
<h3>节奏像真人，七天不动这三样</h3>
<p>第一天只登录和浏览，第二天起正常使用，第三到第七天逐步加时长。不要在注册当天跑批量，也不要在凌晨三点连续操作几小时，时段与行为的不匹配比地址更容易被注意。这七天不改时区、不换浏览器主版本、不绑新支付方式，三件事都会引入新的变化面，真有需要等进入成长期再动。</p>

<h2>三、第 8 到 30 天：成长期，把出口固定下来</h2>

<p>账号过了第一周，开始有行为基线。这个阶段的目标是让基线长出来，稳定性优先于一切。</p>
<h3>出口保持不动，被动迁移也只观察</h3>
<p>同一账号在这 23 天里尽量用同一条出口，中间不主动换。若供应商侧发生被动迁移，记录下来并在后台观察三到五天，不要立刻再手动换一次，连续两次跳变比一次更麻烦。</p>
<h3>可以上轻度自动化，迁移要满足三条</h3>
<p>日常对话、内容生成这类低风险操作可以走脚本，但要控制频率，请求间隔加随机抖动，避免整点整分同时发起。批量任务留到稳定组。迁入稳定组的门槛是：连续 14 天无验证、无异常退出、无强制重新登录，三条都满足才迁，只满足两条的再等一周。</p>

<h2>四、第 31 到 90 天：稳定期，可以承接主业务</h2>
<p>这个阶段的账号已有足够信任积累，可以承担订阅、交付这类不能中断的工作。</p>
<h3>可以按项目重排出口，但一次只动一组</h3>
<p>重排时给每个项目预留一条备用出口，平时不用，主出口异常才切。备用出口要提前做连通性验证，别等要用时才发现鉴权没配。一次只动一组，动完观察一周，同时动多组出问题无法归因。</p>
<h3>最常犯的错：往干净段里塞新号</h3>
<p>因为稳定就不断加号，把新号塞进稳定组已经养好的出口段。这是最常见的一次性污染：一条干净的段被几个新号带脏，整组跟着降级，而修复只能整段退役。加号永远加在新段上，这条规则要写进流程。</p>

<h2>五、第 90 天以后：老号单独成组，维护按周按月走</h2>
<p>老号的价值在于历史，保护历史的方式是「少变」。分组定下来之后，节奏比规则更重要。</p>
<h3>老号组只跑主业务，不参与测试</h3>
<p>除非上游故障，老号组的出口不做主动调整，迁移一次的成本远高于省下的那点月费。必须迁时选同城同运营商的其他段，把地理与 ASN 的变化压到最小。新脚本、新协议、新出口一律先在测试组验证，验证通过再推给老号组，用老号试错是最不划算的操作。</p>
<h3>每周做三件事，每月做两件事</h3>
<p>每周：核对每组账号数与出口数是否一一对应；统计各组本周验证次数，单号超过两次的标出来暂停观察；检查备用出口连通性。每月：按年龄把到期账号迁到下一组，迁前迁后各记一次出口 IP；统计各段污染情况，连续两月出问题的段整体退役。</p>

<h2>常见问答</h2>
<h3>老号和新号能不能共用一条出口？</h3>
<p>答：不建议。共用会让新号的不稳定行为落在老号的出口上，等于用老号的信用替新号背书，一旦新号触发风控，同段的老号也会被一起检查。宁可多买一条便宜段，也别混。</p>
<h3>账号一直很稳，还需要按时间迁移吗？</h3>
<p>答：需要。迁移不是因为你出问题，而是为了让分组反映真实年龄。长期不迁移，稳定组会堆满老号，新号无处可放，最后又回到混跑。</p>
<h3>迁移时换出口还是保留原出口？</h3>
<p>答：优先保留原出口，只改组别标签。确实需要换的，选同城同运营商的不同段，一次只换一个号，观察三天再换下一个。</p>
<h3>三组够用吗，会不会太粗？</h3>
<p>答：起步够用。组太细会增加维护成本，也容易记错。等账号数超过五十，再考虑在稳定组内按项目二次划分。</p>
